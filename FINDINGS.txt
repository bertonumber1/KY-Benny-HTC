1. HOW THE RADIO EXPOSES ITSELF OVER BLUETOOTH  (Windows PnP enumeration)
------------------------------------------------------------------------
The radio pairs to Windows and presents THREE distinct channels:

  (a) BLE GATT — Benshi service 00001100-d102-11e1-9b23-00025b00a5a5
        write char    00001101-...-a5a5   (commands OUT)
        indicate char 00001102-...-a5a5   (replies / events IN)
      Enumerated as BTHLEDEVICE\{00001100-...}_38D200013ECC.

  (b) Classic RFCOMM / GAIA SPP — service UUID 00001101 (SPP)
        Exposed by Windows as a serial port: "Standard Serial over
        Bluetooth link (COM5)".  <-- THE WORKING CONTROL PATH ON WINDOWS.
        Enumerated as BTHENUM\{00001101-...}_..._38D200013ECC.

  (c) Hands-Free Profile — service UUID 0000111F
        "VR-N7600 Hands-Free HF".  <-- the classic-BT VOICE audio path.

Same command set rides both (a) BLE and (b) RFCOMM; only the framing
differs (see section 3).

                      gets clean replies from the radio. This is the
                      transport the Windows web UI should use.

  PROVEN 2026-07-15: sent GET_DEV_INFO + GET_HT_STATUS over COM5, got:
     raw: ff 01 00 05 00 02 80 04 00 00 01 00 92
          ff 01 00 05 00 02 80 14 00 80 01 00 00
     decoded:
          group=2 GET_DEV_INFO +REPLY  payload=00 00 01 00 92  (status 00 OK)
          group=2 GET_HT_STATUS+REPLY  payload=00 80 01 00 00  (status 00 OK)

3. FRAME FORMATS  (from benshi.py, confirmed on the wire)
------------------------------------------------------------------------
Command groups:   BASIC = 2 (0x0002),  EXTENDED = 10 (0x000A)
Reply bit:        command id | 0x8000  marks a reply.
Events:           group=BASIC, cmd=EVENT_NOTIFICATION(9), no reply bit,
                  payload[0] = event type.
Reply payloads:   payload[0] is a STATUS byte (0x00 = OK).
All bitfields are MSB-first big-endian.

  BLE GATT frame (write to ...1101, indicated on ...1102):
        [group:u16be][cmd:u16be][payload...]

  RFCOMM / GAIA frame (COM5 serial):
        [0xFF][0x01][flags][len(payload)][group:u16be][cmd:u16be][payload]
        (+1 trailing XOR checksum byte if flags bit0 set; we send flags=0)
      Incremental parse: resync to 0xFF, need >=8 bytes, total =
        8 + payload_len + (1 if flags&1).

6b. COM5 / OUTGOING SPP LINK BEHAVIOUR  (operational)
------------------------------------------------------------------------
COM5 is an *outgoing* SPP port: the RFCOMM link to the radio is established
on demand when the port is OPENED, and torn down when closed / when the
radio's classic-BT link drops. Consequences:
  - First open after the radio's link is active  -> works (proven, sec 2).
  - Later opens can fail even though Windows still lists the device "OK":
        OSError 1256 "The remote system is not available"
        OSError 1167 "The device is not connected"
    "OK" in Get-PnpDevice = bond is healthy, NOT that a live link exists.
  - Failure causes seen: radio asleep / out of range; the radio's single
    classic-BT slot already taken (e.g. it re-connected to the Pi, which
    also auto-connects); or a stale handle not yet released.
  - To get a live capture: radio awake + in range + NOT connected elsewhere
    (disconnect it from the Pi's webui first), then open COM5.
Windows also exposes COM4 = incoming SPP (LOCALMFG, not the radio) — use
COM5 (the ..._38D200013ECC node) for the radio.

6c. SETTINGS READ / EDIT / WRITE PATTERN  (template for every tab)
------------------------------------------------------------------------
The clean cycle for any editable block is GET -> edit -> WRITE (-> STORE):
  GET   : READ_SETTINGS(10)  -> radio returns the full settings struct;
          parse to fields.  (Also READ_RF_CH 13, READ_BSS_SETTINGS 33,
          GET_APRS_PATH 72 for the other tabs.)
  WRITE : WRITE_SETTINGS(11) with the full struct back (edited fields
          merged over the last-read struct — you must send the WHOLE block,
          not just the delta).
  STORE : STORE_SETTINGS(12) to persist to flash (optional; without it the
          change is live but lost on power-cycle).
Implemented in the webui:
  radio.py  read_settings()  -> READ_SETTINGS, emits "settings"
            write_settings(updates, store) -> merge + WRITE_SETTINGS (+STORE)
  app.py    GET  /api/settings?refresh=1  -> live read from radio
            POST /api/settings {updates, store} -> write back
  index.html Settings tab: "GET from radio" (live read, fills form) and
            "Write to radio" ("persist to flash" checkbox = STORE).
  NOTE: the old "reload" button only re-rendered CACHED state (no radio
  access) — replaced with a true "GET from radio". Keep this distinction
  for the other tabs (redraw-from-cache vs read-from-radio).

  IMPORT / EXPORT (client-side settings profiles):
    Export…  -> downloads the current form as JSON:
                {_type:"vrn7600-settings",_version:1,_exported,mac,fields{}}
    Import…  -> loads a JSON profile into the form; accepts {fields:{}} or a
                bare field map; validates against known fields (unknown keys
                ignored); does NOT auto-write — user reviews then
                "Write to radio". Round-trip verified 2026-07-15.
    Use this to clone a radio's config, back it up, or share known-good
    profiles. Same pattern will extend to channel lists / APRS config.

6d. HOW TO CAPTURE "ALL THE COMMANDS"  (two distinct modes)
------------------------------------------------------------------------
The radio accepts ONE connection per transport at a time. You cannot see
another client's traffic just by connecting yourself — connecting is an
ACTIVE session where YOU issue the commands. So there are two modes, and
they are mutually exclusive on one radio:

  MODE 1 — ACTIVE PROBE (our tool holds the link).
     btdebug.py connects (BLE monitor <MAC>, or gaia COM5) and we walk the
     command set ourselves; every request/reply is logged + cataloged.
     Requirement: the phone/vendor app and any other client are DISCONNECTED.
     Good for: systematically enumerating what each command returns.

  MODE 2 — PASSIVE HCI SNIFF (vendor app drives, we log the radio traffic).
     Run the real vendor app against the radio while capturing the host's
     Bluetooth HCI stream, then analyse the log offline. This captures the
     EXACT command sequences/payloads the official app uses — the best
     source for building UI tabs.
       - Windows: enable HCI logging (btsnoop) / Bluetooth Internal Logger,
         or use a USB BT sniffer; open the btsnoop log after.
       - Linux (the Pi): `sudo btmon -w capture.btsnoop` while the app runs.
     Good for: real-world flows, defaults, edge cases we'd never guess.

  NOTE (2026-07-15): intermittent COM5 "remote system not available" was
  contention — the operator was connecting/disconnecting on Windows at the
  same time as our tools, so we kept bumping each other off the one radio.
  Coordinate: either WE hold it (mode 1) or the app holds it WITH an HCI
  capture running (mode 2). Connecting yourself with no capture shows us
  nothing.

10. HOW THE APP STARTS  (desktop application, not a dev server)
------------------------------------------------------------------------
Three ways, simplest last:
  a) Dev server:      python app.py           -> uvicorn on :8084, use browser
  b) App launcher:    python launcher.py      -> starts the server in a thread
        and opens the UI in its OWN native window (pywebview; WebView2 on
        Windows, GTK/Qt on Linux). Falls back to the default browser if no
        desktop webview. Closing the window stops the server.
  c) Packaged app:    python build.py         -> dist/"VR-N7600 Remote".exe
        A single-file, no-console, double-click desktop app (PyInstaller
        --onefile --windowed). No Python needed on the target machine.
        Linux build of the same script produces dist/"VR-N7600 Remote".

Packaging notes:
  - app.py is frozen-aware: when sys.frozen, static assets load from _MEIPASS
    (bundled, read-only) and config.json is read/written next to the .exe
    (writable, persists between runs). In dev both are the project dir.
  - build.py bundles static/ and --collect-all bleak + webview (their platform
    backends load dynamically). macOS/Android backend warnings are harmless.
  - The server still binds 0.0.0.0:<port>, so phones / other LAN devices reach
    the same UI at http://<machine>:<port> even when run as a desktop app.
  - Default config (no file present) is now auto_connect=false, transport=ble.

STRUCTURAL DECODE (offline analysis of the captures above):
  - READ_FREQ_RANGE == ADV_SETTINGS2[:21] EXACTLY. So ADV_SETTINGS2 =
    [21B freq-range preamble] + [40B of ADV2-specific data].
  - ADV_SETTINGS[:21] has the SAME layout but different values at bytes
    6, 8, 14, 16 (90/92/ae/b8 vs 88/e1/90/e0) — a second instance of the
    same range struct (RX vs TX, or range-set 2). Body after byte 21 (102B)
    contains an arithmetic step-table at bytes 37..45 = 19 1b 1d 1f 21 23 25
    27 29 (+2 each) — an RF/AGC calibration lookup table.
  - DevInfo.freq_range_count = 5, so the 20 data bytes of FREQ_RANGE are
    plausibly 5 ranges x 4 bytes; exact freq encoding still TBD (values don't
    map to MHz as raw u16be — needs calibration vs the radio's real ranges).
  - ALL blocks are STATIC across repeated reads (no volatile bytes) => they
    are config/calibration, so any byte that changes between two captures is a
    genuine setting change. Clean differential RE, no live-measurement noise.

TOOL: adv_re.py  (capture / diff). Workflow to map a field:
    python adv_re.py capture before
    <change ONE setting ON THE RADIO or via the web UI>
    python adv_re.py capture after
    python adv_re.py diff captures/adv-before-*.json captures/adv-after-*.json
  Baseline saved: captures/adv-baseline-*.json.

BLOCKER for the live differential: the radio power-saves VERY aggressively and
drops the BLE link within seconds of idle ("Device ... was not found"). To run
the toggle-and-diff pass it must be kept awake (on charge + auto_power_off
disabled, or actively held connected). This aggressive sleep is also the root
cause of the intermittent connection drops seen throughout.

11b. "PAIRING" TICKBOX + STAYING CONNECTED + PROBING THE LIVE LINK
------------------------------------------------------------------------
- The radio's on-screen "pairing" tickbox (~30 s) only matters for the FIRST
  bond with a new device. Once bonded (Windows lists VR-N7600 as paired), it
  is irrelevant — connecting reuses the stored bond. "Stay connected" does NOT
  depend on it.
- Keep-alive: the status poll doubles as a keep-alive so the link isn't idled
  out. Tightened to 15 s (was 30) to sit under any idle timeout. Verified
  2026-07-15: link held >45 s past connect, battery/status updating.
- SINGLE-CONNECTION RULE: BLE (and classic) accept ONE connection at a time.
  A separate btdebug/probe process CANNOT open a 2nd link while the webui holds
  it — they collide. SOLUTION: probe THROUGH the live webui link:
      POST /api/debug/command  {cmd:<int>, payload_hex:"", timeout:3.0}
      -> {cmd_name, reply_hex, reply_len, status}
  Backed by radio.raw_command() (raw reply, no success-check). Verified:
  connected via UI, probed 3 advanced blocks, link still up afterwards.

11d. PF (PROGRAMMABLE FUNCTION) KEYS — protocol DECODED & verified
------------------------------------------------------------------------
GET_PF(55) reply = status(00) + 16 (key_id, action) pairs (32 bytes).
  Fixed key_id order (hardware slots):
    06 08 04 02 16 18 14 12 26 28 24 22 36 38 34 32
GET_PF_ACTIONS(75) reply = status + list of the VALID action codes:
    01 02 17 13 0c 11 12 03 1b 1c 04 05 06 0f 18 19 1f 1d 1e 07 08 0a 0b
    15 16 09 0d 0e 10 14   (0x00 = unassigned)
SET_PF(56) request = the 16 ACTION bytes ONLY, in the fixed key order above
  (NOT key/action pairs — sending pairs mis-writes it). Reply = status.
  VERIFIED 2026-07-15: identity write, observed scramble, wrote correct

    RX tail : ht c0 41 00 04 | rf 00 00 24 26 7f 30 32 07 00 02 a5 20 ...
  Decoded:
  * HT_STATUS bit1 ("is_in_tx" in benlink/HTCommander) is really
    "TX **or** ~5 s post-RX channel-hold": after EVERY squelch close the
    radio pushes bit1=1 for ~5 s, then 0. This is why the web TX lamp lit
    on receive. Same value from event and poll — radio-genuine, not a
    decode bug.
  * RF_STATUS byte10 disambiguates: 0x81 idle · 0xa1 real TX · 0xa5 hold
    (bit5 = PA path context, bit2 = hold window). byte1 0x29-2b idle/RX ->
    0x00 in TX/hold; bytes2-3 24 26 idle -> 31 33 with squelch open
    (noise-floor levels); byte4 pegs 0x7f in TX/hold; byte7 0x87 -> 0x07
    when b1 low.
  * Web UI now derives the TX lamp: our own PTT = TX; else rf byte10
    bit2 clear = TX; else within 6 s of RX = channel-hold (shown BUSY).
  * DO_PROG_FUNC(66) [effect, state] is ACKed (status 00) for ANY effect
    but is INERT on fw147 — VOL_DOWN/VOL_UP cycles left volume untouched
    (matches MAIN_PTT finding in §12). Remote "button press" is a dead
    end; use the real setting writes instead (MON key = SQL 0/restore).

12b. THE REAL AUDIO PATH — "BS AOC" vendor RFCOMM channel (from HTCommander
     src: windows/runner/bluetooth_classic_plugin.cpp, lib/radio/
     audio_engine.dart, lib/radio/radio_audio.dart — confirmed working code
     for these radios; explains the is_aoc_connected flag in HT_STATUS):
  - Service UUID 39144315-32FA-40DB-85ED-FBFEBA2D86E6 (RFCOMM ch 2);
    fallback Generic Audio 0x1203. NO Windows COM port is auto-created for
    a vendor UUID -> connect via WinRT RfcommDeviceService + StreamSocket
    (winrt-Windows.Devices.Bluetooth.Rfcomm + winrt-Windows.Networking.Sockets
    — INSTALLED in the venv).
  - Framing: 0x7e-delimited (HDLC-ish), 0x7d escape = next byte XOR 0x20.
    First unescaped byte = cmd:
        0x00 TX audio (us->radio; also RX variant), 0x03 RX audio,
        0x01 audio end, 0x02 audio ACK, 0x09 TX echo (metering only).
    Payload after cmd byte = concatenated SBC frames (<300 B per 0x7e frame).
  - Codec: SBC 32 kHz mono, 16 blocks, 8 subbands, loudness allocation,
    bitpool 18 (radio default; 40 confirmed working OTA, 124 rejected).
  - PTT: radio KEYS AUTOMATICALLY when SBC audio frames arrive on this
    channel (pace at real-time, ~64000 B/s PCM); UNKEY by sending the end
    frame: 7e 01 00 01 00 00 00 00 00 00 7e. No control-channel command.
  - scratchpad/aoc_probe.py written (WinRT connect + frame dump), not yet
    run against the radio.

14. FIRMWARE / FOTA — does the vendor app need root?  (answered 2026-07-16)
------------------------------------------------------------------------
No. Nothing in the decompiled app shells out or escalates: no Runtime.exec of
su, no /system/bin, no magisk/superuser anywhere under sources/. Android apps
can't get root normally and this one doesn't try. "FOTA" is split in two:
  - CLOUD CHECK: DeviceManagement gRPC service, method CheckFirmwareUpdate,
    returns FirmwareInfo{url, md5, version} (see rpc/Dm.java, DeviceManagement
    Grpc.java). The phone just downloads the blob from that URL.
  - RADIO FLASH: NOT in the radio's own BT command set (cmds 1..77 have no
    firmware/flash/OTA op). So the push happens out-of-band of the control
    protocol we speak — the radio is rebooted into a bootloader/DFU mode and
    the image is written over a separate BLE/SCO channel (standard for these
    SoCs). No phone privilege is involved; it's ordinary BLE writes to the
    device's upgrade endpoint. We have NOT reverse-engineered that path (and
    it's the one place a bad write can brick the radio, so leave it last).
